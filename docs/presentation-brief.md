## 2. Проект в двух словах

**Bito** — онлайн-дурак в реальном времени. Игроки садятся за стол со ставкой в виртуальной валюте: проигравший платит, победители делят банк по местам. Никаких реальных денег.

- Игра 1 на 1 с подбором соперника или компания на 3–6 игроков
- Два режима: **подкидной** и **переводной**, три размера колоды: 24, 36, 52 карты
- Всё считает сервер, браузер только отправляет намерения («хожу этой картой»)
- Экономика с журналом операций: баланс всегда сходится

**Одна фраза для титула:** «Дурак онлайн: игра в реальном времени с честной экономикой».

## 5. Архитектура (слайд 5)

```
┌────────────────────┐     REST /api/v1  (логин, профиль, столы, кошелёк)
│  Браузер           │ ──────────────────────────────┐
│  Vue 3 + TypeScript│                               ▼
│                    │     WebSocket /ws       ┌──────────────────┐        ┌──────────────┐
│                    │ ◄──────────────────────►│   Go-сервер      │ ◄────► │ PostgreSQL   │
└────────────────────┘     (ход игры)          │                  │        │ пользователи,│
                                               │  HTTP  +  Hub    │        │ партии, деньги│
                                               │  Room (горутина  │        └──────────────┘
                                               │  на каждый стол) │ ◄────► ┌──────────────┐
                                               │  Game (правила)  │        │ Redis        │
                                               └──────────────────┘        │ сессии, коды │
                                                        │                  └──────────────┘
                                                        ▼
                                                 SMTP (письма с кодом)
```

**Слои на сервере** (идея: каждый слой знает только о соседнем):

| Слой | Папка | Роль |
|---|---|---|
| Транспорт | `delivery/http`, `delivery/ws` | принимает запросы и сообщения |
| Правила игры | `game` | чистая логика дурака без сети и БД |
| Экономика | `economy` | чистая математика выплат |
| Сервисы | `service` | регистрация, профиль |
| Хранилище | `repository/postgres`, `repository/redis` | SQL и Redis |

Два канала не случайны: **REST** для разовых действий (войти, создать стол), **WebSocket** для живой игры, где сервер сам толкает обновления.

## 7. Реальное время (слайд 8)

Идея: **каждый стол это отдельная горутина `Room`**, внутри неё цикл на каналах. Она одна владеет состоянием игры, поэтому не нужны блокировки вокруг правил.

```
Игрок A ─┐                       ┌─ game_state ─► Игрок A
Игрок B ─┼─ сообщение ─► Room ───┤
Игрок C ─┘   (канал)     │      └─ game_state ─► Игрок B, C
                         ▼
                   Game (правила)
```

| Что | Как |
|---|---|
| Сервер главный | клиент шлёт `attack`, `defend`, `take`, `pass`, `transfer`, `surrender`; допустимость проверяет только сервер |
| Руки не видны | каждому игроку приходит только его рука и количество карт у остальных |
| Таймер хода | 20 секунд; если время вышло, сервер ходит за игрока: защитник берёт карты, атакующий кладёт карту сам, остальные пасуют (партия не зависает) |
| Обрыв связи | 30 секунд на возвращение, затем автосдача |
| Возврат за стол | после перезагрузки страницы лобби показывает «Вернуться за стол» |

Сообщения сервера: `game_state`, `game_over`, `timer_tick`, `player_disconnected`, `player_reconnected`, `chat`, `error`.

**Лобби тоже на сокете.** Отдельное соединение `/ws/lobby` и своя горутина `Lobby`: она знает, кто онлайн, раз в 2 секунды берёт список открытых столов и рассылает `lobby_state` только при изменении. Если сокет недоступен, лобби само переходит на опрос `GET /tables`.

### 8.1. ER-диаграмма

```
                 ┌──────────────┐
                 │    users     │
                 │──────────────│
                 │ id  (PK)     │
                 │ email, name  │
                 │ password_hash│
                 │ deleted_at   │
                 └──────┬───────┘
          1:1           │ 1:1            1:N            1:N
   ┌────────────────────┼───────────────┬──────────────────────────┐
   ▼                    ▼               ▼                          ▼
┌────────────┐   ┌──────────────┐  ┌────────────────┐   ┌────────────────────┐
│ user_stats │   │ user_wallets │  │ oauth_accounts │   │   game_players     │
│ wins       │   │ balance ≥ 0  │  │ provider       │   │ place, outcome     │
│ losses     │   │ last_top_up  │  └────────────────┘   │ payout             │
│ total_games│   └──────────────┘                       └─────────┬──────────┘
└────────────┘                                                    │ N:1
                                                                  ▼
┌─────────────────────┐    N:1 (game_id)               ┌───────────────────┐
│ wallet_transactions │ ─────────────────────────────► │      games        │
│ amount, kind        │                                │ mode, deck, stake │
│ balance_after       │ ◄─ N:1 user_id ── users        │ fee, status       │
└─────────────────────┘                                └───────────────────┘

┌──────────────────────┐
│     friendships      │ ── user_low  ──► users (N:1)
│ user_low < user_high │ ── user_high ──► users (N:1)
│ requested_by, status │    PK (user_low, user_high): одна строка на пару
└──────────────────────┘
```

### 8.2. Таблицы

| Таблица | Назначение | Ключевое |
|---|---|---|
| `users` | аккаунты | мягкое удаление (`deleted_at`), уникальные email и имя без учёта регистра |
| `user_stats` | победы, поражения, число игр | 1:1 с пользователем |
| `user_wallets` | баланс | `CHECK (balance >= 0)`, по умолчанию 2500, `last_top_up_at` для подачки |
| `oauth_accounts` | привязки соцсетей | подготовка под вход через внешние сервисы |
| `friendships` | дружба и заявки | одна строка на пару: `CHECK (user_low < user_high)`, кто отправил заявку, статус `pending` или `accepted` |
| `games` | партия: режим, колода, ставка, комиссия, статус | `status`: playing, finished, draw, refunded |
| `game_players` | кто играл, место, исход, итог | PK (`game_id`, `user_id`) |
| `wallet_transactions` | **журнал каждого движения денег** | `amount`, `kind`, `balance_after`, индекс по игроку и времени |

### 8.3. Что защищает данные на уровне БД

| Ограничение | Что гарантирует |
|---|---|
| `CHECK (balance >= 0)` | баланс никогда не уйдёт в минус, даже при ошибке в коде |
| `CHECK (stake > 0)`, `fee >= 0` | ставки и комиссия осмысленные |
| `CHECK (status IN (...))`, `outcome IN (...)` | только допустимые статусы |
| `ON DELETE RESTRICT` на журнале и игроках | историю денег нельзя стереть каскадом |
| Составной PK `(game_id, user_id)` | игрок не окажется в партии дважды |
| Журнал + `balance_after` | баланс игрока всегда равен сумме его операций |

**Проверка целостности одним запросом** (должен вернуть 0 строк):

```sql
SELECT w.user_id
FROM user_wallets w
LEFT JOIN wallet_transactions t USING (user_id)
GROUP BY w.user_id, w.balance
HAVING w.balance <> COALESCE(SUM(t.amount), 0);
```

### 8.4. Виды операций в журнале

| `kind` | Когда |
|---|---|
| `signup_bonus` | стартовые 2500 при регистрации |
| `stake_lock` | ставка списана на старте партии |
| `win_payout` | победитель получил ставку и свою долю |
| `stake_refund` | ставка возвращена (ничья или сбой сервера) |
| `top_up` | подачка при балансе ниже 100 |
| `opening` | входящий остаток существовавших игроков |

## 9. Экономика (слайд 10)

**Правила**

| Параметр | Значение |
|---|---|
| Стартовый баланс | 2500 |
| Допустимые ставки | 100 · 250 · 500 · 1000 · 2500 · 5000 |
| Комиссия | 5% с ставок проигравших |
| Подачка | если баланс ниже 100: пополнение до 500, не чаще раза в час |
| Валюта | только виртуальная |

**Как делятся деньги**

1. На старте партии ставка списывается у всех (одна транзакция на весь стол).
2. Проигравшие: дурак и все сдавшиеся. Их ставки образуют пул.
3. Из пула вычитается комиссия 5%.
4. Остаток делится между победителями **по местам**: кто вышел первым, берёт больше.
5. Каждый победитель дополнительно получает **свою ставку обратно**, поэтому не уходит в минус.

**Доля места** `i` среди `m` победителей: `(m − i + 1) / (m·(m+1)/2)`

| Победителей | Доли по местам |
|---|---|
| 1 | 100% |
| 2 | 67% / 33% |
| 3 | 50% / 33% / 17% |

**Пример: 4 игрока, ставка 500**

| Игрок | Итог |
|---|---|
| Дурак | **−500** |
| Комиссия | 25 |
| 1 место | **+238** |
| 2 место | **+158** |
| 3 место | **+79** |

Проверка: 238 + 158 + 79 − 500 = **−25**, ровно комиссия. Деньги не появляются и не исчезают, это проверяется тестом на всех ставках и числах игроков от 2 до 6.

**Отдельные случаи:** ничья — всем возвращается ставка без комиссии; сдача и отключение больше 30 секунд — проигрыш; выплата не записалась в БД — три повтора, затем ставки партии возвращаются сразу; сервер упал посреди партии — при старте ставки возвращаются автоматически.

## 10. Надёжность и безопасность (слайд 11)

| Что | Как реализовано |
|---|---|
| Пароли | хранятся хэшем bcrypt, не в открытом виде |
| Авторизация | JWT: токен доступа живёт 15 минут, refresh-сессия 7 суток хранится в Redis и отзывается при выходе; токены лежат в cookie, сокет авторизуется по cookie, и токен не попадает в URL и логи |
| Регистрация | код подтверждения приходит в письмо, живёт ограниченное время (Redis, TTL) и сгорает после 5 неверных попыток |
| Перебор паролей | вход и отправка кода: не больше 10 попыток на почту и 50 на IP за 15 минут, дальше ответ 429 |
| Боевой режим | сервер не запустится со слабым секретом JWT (короче 32 байт), cookie помечены `Secure` |
| Честная игра | сервер проверяет каждый ход, чужие карты клиенту не передаются |
| Деньги | списание и выплата в одной SQL-транзакции; повторная выплата невозможна (статус партии `playing` → `finished` меняется один раз) |
| Один аккаунт, один стол | нельзя сесть за два стола с одной ставкой и держать больше одного открытого стола |
| Восстановление | если выплата не прошла, сервер повторяет её 3 раза, а затем сразу возвращает ставки этой партии; при старте возвращает ставки зависших партий |
| Миграции | SQL-миграции встроены в бинарник и применяются при старте сервера, каждая в своей транзакции |
| Защита от гонок | списание ставки одним атомарным запросом `UPDATE … WHERE balance >= ставка`; порядок блокировок строк одинаковый, взаимных блокировок нет |

| **Лидерборд** | таблица лучших игроков (интерфейс готов, сервер следующим этапом) |

> [!warning] Не говорить, что готово
> Интерфейс есть, а бэкенда ещё нет у: **магазина** и **лидерборда** (в лобби они показаны на заглушках). Если комиссия спросит, это честно называется «интерфейс спроектирован, серверная часть следующим этапом».

## 15. Вопросы комиссии и ответы

| Вопрос | Ответ |
|---|---|
| **Почему Go?** | Горутины и каналы подходят под модель «стол = горутина», сервер один бинарник, быстро стартует |
| **Почему WebSocket, а не опрос?** | В игре сервер сам должен сообщать о ходах и таймере, опрос дал бы задержки и лишнюю нагрузку |
| **Почему две базы?** | PostgreSQL для данных, которые нельзя терять и нужно считать, Redis для того, что должно само истекать (коды, сессии) |
| **Почему без рейтинга Elo?** | В дураке большую роль играет раздача; для игры на ставки нужен баланс, а не рейтинг. Ставки дают понятную мотивацию |
| **Как защищаетесь от читов?** | Правила проверяет сервер. Клиент шлёт только намерение хода; чужие карты ему не отправляются |
| **А если сервер упадёт?** | Ставки зависших партий возвращаются при следующем старте автоматически, всё в одной транзакции |
| **Как гарантируете, что деньги не теряются?** | Одна транзакция на списание и на выплату, журнал с `balance_after`, `CHECK` на баланс и тест-инвариант |
| **Это можно масштабировать?** | Сейчас один процесс, комнаты в памяти. Для нескольких серверов понадобятся общий реестр комнат (Redis) и привязка игрока к серверу. Для задачи проекта это сознательное упрощение |
| **Почему виртуальная валюта?** | Реальные деньги это азартные игры с юридическими ограничениями; виртуальная валюта убирает проблему |
| **Что делали сами?** | Игровой движок, экономику и выплаты, базу, WebSocket-комнаты, фронт и анимации. Использованы готовые библиотеки из раздела 6 |

> [!note] Если спросят про нерешённое
> Сервер работает одним процессом, комнаты живут в памяти (см. вопрос о масштабировании). Магазин и лидерборд ещё не подключены к серверу.

## 16. План живой демонстрации (2–3 минуты)

1. Войти двумя аккаунтами (два окна браузера).
2. Первый создаёт стол на 2 игрока со ставкой 100, второй садится.
3. Сыграть пару ходов: атака, защита, переход хода.
4. Показать чат и быструю фразу.
5. Партия заканчивается: окно итога с `+95 / −100`.
6. В профиле видна история партий, баланс изменился.
7. (Если есть время) в БД показать строки `wallet_transactions` этой партии.

Запасной план: заранее записанное видео партии на 30–40 секунд, если не будет сети или докер не поднимется.
