# Лобби-сокет: учебный план

> [!abstract] Что строим
> Игрок в лобби держит открытое WebSocket-соединение `/ws/lobby`. Сервер сам присылает ему список открытых столов и число игроков онлайн, как только что-то изменилось. Опрос `GET /tables` по таймеру уходит в запасной вариант.
> Связанные заметки: [[features]] (пункт 4, P0), [[lobby-plan]] (как устроено лобби).

> Проверено: тесты с `-race`, вход в лобби в браузере, стол, созданный другим игроком, появился без единого `GET /tables`.

## Шаг 1. Lobby: горутина и счётчик онлайна

### Зачем

Лобби должно знать, кто подключён. Этот список одновременно трогают много горутин: каждое соединение живёт в своих `ReadPump` и `WritePump`. Нужен способ менять общий список без гонок.

### Теория

> [!note] Горутина-владелец
> Девиз Go: *«Не общайтесь через общую память. Делитесь памятью через общение»*.
> Данные (карту `clients`) читает и пишет **ровно одна горутина**, цикл `Run`. Остальные не трогают карту, а **присылают просьбу** в канал. Раз владелец один, мьютекс вокруг карты не нужен: просьбы приходят по одной.
> Так уже сделан `Room.Run` в `room.go`: `register`, `unregister`, `incoming` — это просьбы, а `select` разбирает их по очереди.

> [!note] `select`
> `select` ждёт сразу несколько каналов и выполняет ту ветку, которая готова первой. Готовы несколько — выбирает случайную. Ветка `default` делает `select` неблокирующим: если никто не готов, сразу выполняется `default`.

> [!note] Буферизованный и небуферизованный канал
> `make(chan T)`: отправитель ждёт, пока получатель заберёт значение. Это «рукопожатие».
> `make(chan T, n)`: отправитель ждёт, только если буфер полон.
> Для `register` и `unregister` достаточно небуферизованных: `Run` быстро их разбирает.

> [!note] `close(stop)` как сигнал всем
> Из закрытого канала чтение сразу возвращает нулевое значение, **у всех читателей одновременно**. Поэтому `close(stop)` — способ сказать «стоп» любому числу горутин. Закрывать канал можно только один раз, иначе паника; посмотри, как это защищено в `Room.Close`.

> [!note] Канал-запрос с ответом
> Как узнать `Online()` из чужой горутины, не трогая карту? Отправить владельцу **канал для ответа**:
> ```go
> reply := make(chan int)
> l.queries <- reply
> n := <-reply
> ```
> Владелец в `select` получает `reply` и отвечает `reply <- len(...)`. Приём называется *request–response через канал*.
> Второй способ: хранить число в `atomic.Int32` и обновлять из `Run` после каждого изменения (так сделан `playersCount` в `Room`). Сравни оба способа, это хороший вопрос для защиты.

> [!note] Гонка данных и `-race`
> Гонка — это когда две горутины одновременно обращаются к одной памяти и хотя бы одна пишет. Программа может месяцами «работать», а потом упасть или посчитать мусор. Флаг `-race` включает детектор: он ловит гонки, которые реально случились во время теста.

### Практика

Файл `internal/delivery/ws/lobby.go`:

- `type Lobby struct`:
  - `clients map[string]map[*Client]bool`: id игрока → набор его соединений (две вкладки — два соединения, а игрок онлайн один);
  - `register`, `unregister chan *Client`;
  - канал запросов для `Online()`;
  - `stop chan struct{}` и защита от двойного закрытия.
- `NewLobby() *Lobby`.
- `Run()`: цикл `for { select { ... } }`:
  - `register`: создать вложенную карту, если её нет, и добавить соединение;
  - `unregister`: удалить соединение; если у игрока пусто, удалить игрока; вызвать `c.Close()`;
  - запрос онлайна: ответить числом игроков (не соединений);
  - `stop`: закрыть всех клиентов и выйти.
- `Register(c *Client) bool`: отправить в `register`, но не зависнуть, если лобби уже остановлено. Подсмотри `Room.RegisterClient`.
- `Online() int`, `Close()`.

Файл `internal/delivery/ws/lobby_test.go`:

- клиентов создавай без соединения, как `createTestClient` в `room_test.go` (`conn: nil`);
- сценарий: A (вкладка 1), A (вкладка 2), B → `Online() == 2`; ушла вкладка 1 → `2`; ушла вкладка 2 → `1`;
- **без `time.Sleep`**: `Online()` сам синхронизирует тест с `Run`, потому что ответ приходит только после того, как обработаны предыдущие просьбы. Подумай, почему это так.

```bash
go test -race ./internal/delivery/ws/ -run Lobby -v
```

> [!warning] Ловушки
> - Чтение `len(l.clients)` прямо в `Online()` без канала: `-race` это поймает.
> - Удаление из вложенной карты без удаления пустого игрока: онлайн не уменьшится.
> - `Unregister` уже закрытого клиента: `Close` у `Client` защищён флагом `closed`, проверь, что повторный вызов безопасен.

### Проверь себя

> [!question]- Почему карту `clients` не нужно защищать мьютексом?
> Её трогает только горутина `Run`. Все остальные присылают просьбы через каналы, а `Run` обрабатывает их по одной. Одновременного доступа нет, значит, нет и гонки.

> [!question]- Что случится, если вызвать `l.register <- c` после того, как `Run` вышел?
> Небуферизованный канал: отправка ждёт получателя, а его больше нет. Горутина зависнет навсегда (утечка). Поэтому отправка делается в `select` вместе с `<-l.stop`: если лобби остановлено, срабатывает ветка `stop`.

> [!question]- Почему тест не нуждается в `time.Sleep` перед проверкой `Online()`?
> Запрос онлайна — такая же просьба в цикл `Run`, как `register`. Если `register` отправлен небуферизованным каналом, то к моменту возврата отправки `Run` его уже принял, а следующую просьбу (запрос онлайна) обработает только после. Порядок гарантирован каналами, а не временем.

> [!question]- Канал-запрос или `atomic`: что выбрать для `Online()`?
> `atomic` быстрее и не может зависнуть, но число чуть-чуть отстаёт от карты (обновляется после обработки). Канал-запрос даёт точное значение, но зависнет, если `Run` не работает (нужен `select` со `stop`). Для счётчика онлайна в лобби оба годятся; в `Room` выбран `atomic`.

> [!question]- Зачем вложенная карта, а не `map[string]*Client`?
> У игрока может быть несколько вкладок. С плоской картой вторая вкладка затёрла бы первую, а закрытие любой из них сделало бы игрока «офлайн», хотя вторая вкладка открыта.

- [ ] в коде нет обращения к `l.clients` вне `Run`

## Шаг 2. Отвязать Client от Room

### Зачем

`ReadPump` сейчас знает про `Room`: пишет в `c.room.incoming` и `c.room.unregister`. Чтобы тот же `Client` жил в лобби, он должен зависеть не от конкретного типа, а от **того, что ему нужно**: «куда отдать входящее сообщение» и «кому сказать, что я ушёл».

### Теория

> [!note] Интерфейсы в Go реализуются неявно
> Нет слова `implements`. Тип подходит под интерфейс, если у него есть нужные методы. Поэтому интерфейс объявляют **там, где его используют** (у потребителя), а не рядом с реализацией. Пример в проекте: `TokenValidator` и `Bank` объявлены в пакете `ws`, который их вызывает.

> [!note] Маленькие интерфейсы
> «Чем больше интерфейс, тем слабее абстракция». Интерфейс из одного-двух методов легко реализовать и подменить в тесте. Не тащи в него всё, что умеет `Room`.

> [!note] Рефакторинг без изменения поведения
> Сначала меняем форму кода, **не меняя поведения**, и проверяем это старыми тестами. Только потом добавляем новое. Если тесты комнаты остались зелёными, рефакторинг удался.

### Практика

1. В `client.go` замени поле `room *Room` на поле интерфейсного типа. Форма, от которой можно оттолкнуться:
   ```go
   type endpoint interface {
       deliver(IncomingMessage) bool
       leave(*Client)
   }
   ```
   `deliver` возвращает `false`, если получатель остановлен и читать дальше незачем.
2. Перепиши `ReadPump` через эти два метода. `select` со `stop` уезжает внутрь реализаций.
3. Реализуй оба метода у `Room` (та же логика, что сейчас стоит в `ReadPump`).
4. Реализуй их у `Lobby`: `leave` отправляет в `unregister`, а `deliver` пока просто игнорирует сообщение (в лобби клиент ничего не шлёт) и возвращает `true`, пока лобби живо.
5. Поправь `NewClient` и тестовые помощники (`createTestClient` и место около `room_test.go:300`).

```bash
go test -race ./internal/delivery/ws/...
```

> [!warning] Ловушки
> - Методы с маленькой буквы видны только внутри пакета `ws`. Здесь это нормально, наружу интерфейс не нужен.
> - `Room` с указательным получателем: интерфейс реализует `*Room`, а не `Room`.
> - Не меняй ничего в логике комнаты. Если пришлось править `room_test.go` не только в конструкторе клиента, значит, поведение поменялось.

### Проверь себя

> [!question]- Почему интерфейс объявлен в `client.go`, а не в `room.go`?
> Его потребитель — `Client`. В Go интерфейс описывает, что нужно вызывающему, и живёт рядом с ним. Реализации (`Room`, `Lobby`) про интерфейс ничего не знают.

> [!question]- Как проверить на этапе компиляции, что `*Lobby` реализует интерфейс?
> Строка `var _ endpoint = (*Lobby)(nil)`. Если метода не хватает, код не соберётся.

> [!question]- Что даёт этот рефакторинг тестам?
> Клиента можно подключить к фейковому `endpoint` и проверять `ReadPump` отдельно от игры.

### Готово, когда

- [ ] в `client.go` нет слова `Room`
- [ ] все старые тесты пакета `ws` зелёные с `-race`

## Шаг 3. Эндпоинт /ws/lobby

### Зачем

Браузер должен как-то попасть в лобби. Нужен маршрут, который проверит cookie, откроет WebSocket и отдаст клиента в `Lobby`.

### Теория

> [!note] Как открывается WebSocket
> 1. Браузер шлёт обычный HTTP `GET` с заголовками `Upgrade: websocket` и `Connection: Upgrade`.
> 2. Сервер отвечает `101 Switching Protocols`, и с этого момента это не HTTP, а двусторонний канал кадров.
> 3. Всё, что можно проверить кодом ответа (401, 404), проверяй **до** `Upgrade`. После него ответить кодом уже нельзя, только сообщением и закрытием (`rejectConn`).

> [!note] Почему авторизация по cookie
> Браузерный `new WebSocket(url)` не умеет ставить заголовок `Authorization`. Токен в URL (`?token=`) попадает в логи и историю, поэтому в проекте от него ушли (коммит `16ea654`). Cookie `accessToken` браузер прикладывает к рукопожатию сам.
> Обратная сторона cookie — чужой сайт может открыть сокет от имени пользователя. От этого защищает `CheckOrigin` в `NewHub`: пускаем только свои `Origin`.

> [!note] Ping / pong и дедлайны
> Соединение может «умереть» молча (закрыли ноутбук). `WritePump` раз в `pingPeriod` шлёт ping, браузер автоматически отвечает pong, а `ReadPump` продлевает дедлайн чтения. Нет pong за `pongWait` — чтение падает с ошибкой, клиент уходит из лобби. Для лобби это уже работает, ты переиспользуешь те же насосы.

> [!note] Приём «вынести функцию»
> Первые строки `ServeWS` (достать токен, проверить, получить id и имя) нужны и лобби. Копировать их — значит потом чинить в двух местах. Вынеси в метод вроде `h.authenticate(r) (id, name string, ok bool)`.

### Практика

1. В `Hub` добавь поле `lobby *Lobby`. Создай лобби в `NewHub` и запусти `go lobby.Run()`.
2. Вынеси авторизацию из `ServeWS` в отдельный метод и используй его в обоих местах.
3. Напиши `func (h *Hub) ServeLobby(w, r)`: авторизация → `Upgrade` → `NewClient(...)` с лобби в качестве `endpoint` → `Register` → запустить оба насоса.
4. В `internal/delivery/http/server.go` рядом с `/ws` добавь маршрут `/ws/lobby`.
5. Тест по образцу коммита `06ad314` (`http/server_test.go`): без cookie → 401; с cookie → рукопожатие проходит, `Online()` стал 1.

> [!warning] Ловушки
> - Порядок маршрутов в chi не важен, но путь должен совпасть с тем, что проксирует Vite в dev-режиме. Посмотри `web/vite.config.ts`: проксируется ли `/ws` целиком или только точный путь.
> - Не забудь, что после `Upgrade` писать в `w` нельзя.

### Проверь себя

> [!question]- Почему проверку токена нельзя делать после `Upgrade`?
> После `101` HTTP-ответ уже отправлен. Вернуть 401 нельзя, браузер увидит «соединение открылось и сразу закрылось» без понятной причины. Да и лишний апгрейд тратит ресурсы на чужака.

> [!question]- От чего защищает `CheckOrigin`, если есть авторизация?
> Авторизация как раз и есть cookie, а cookie браузер прикладывает к запросу с любого сайта. Без проверки `Origin` вредоносная страница открыла бы сокет от имени залогиненного игрока (атака *Cross-Site WebSocket Hijacking*).

> [!question]- Что произойдёт с лобби, если пользователь закрыл вкладку?
> Браузер закроет соединение, `ReadPump` получит ошибку чтения, вызовет `leave`, `Run` удалит соединение. Если вкладка «умерла» молча, то же случится по дедлайну pong.

### Готово, когда

- [ ] `/ws/lobby` без cookie → 401, с cookie → соединение открыто
- [ ] в DevTools → Network → WS видно открытое соединение с лобби
- [ ] код авторизации живёт в одном месте

## Шаг 4. Рассылка столов

### Зачем

Главное, ради чего всё затевалось: клиент получает список столов и онлайн без запросов, сразу при подключении и потом при каждом изменении.

### Теория

> [!note] Push по событиям или серверный опрос
> **По событиям:** `Room` сообщает лобби о каждом изменении (сел, встал, старт, закрытие). Мгновенно, но точек вызова много, а забытая одна значит «залипший» стол в списке.
> **Серверный опрос с рассылкой по изменению:** лобби раз в 2 секунды само берёт `ListOpenRooms()`, сравнивает с прошлым снимком и рассылает только при изменении. Одна точка, невозможно забыть событие, задержка до 2 секунд.
> Для проекта выбираем второе. Опрос остаётся, но **один на сервере**, а не по одному на каждого клиента.

> [!note] Сравнение снимков
> Проще всего сравнивать уже готовые байты: `json.Marshal` сообщения → `bytes.Equal` с прошлыми. Совпало — молчим. Бонус: рассылаешь тот же срез байтов всем, сериализация одна.
> Подумай, что в `RoomInfo` может меняться без реальных изменений (порядок? время?), из-за чего снимки будут всегда «разные». `ListOpenRooms` сортирует по `CreatedAt`, это помогает.

> [!note] Медленный клиент
> Рассылка идёт из `Run`. Если один клиент не читает, нельзя ждать его, иначе встанут все. `Client.Send` уже неблокирующий: при полном буфере возвращает `false`. Что делать с таким клиентом — реши сам (подсказка: в комнате его просто отключают).

> [!note] Интерфейс-источник и тестируемое время
> Лобби не должно знать про `Hub` целиком. Ему нужен один метод:
> ```go
> type tableSource interface { ListOpenRooms() []RoomInfo }
> ```
> В тесте подставишь фейк с нужными столами. Интервал тикера сделай полем (2 секунды в бою, миллисекунды в тесте), иначе тест будет ждать по 2 секунды.

> [!note] Взаимная блокировка (deadlock)
> `ListOpenRooms` берёт `h.mu.RLock`. Если когда-нибудь `Hub`, держа `h.mu`, будет ждать канал лобби, а лобби в этот момент ждёт `h.mu`, оба встанут навсегда. Правило: **не ждать канал, держа мьютекс**. Опрос из лобби эту проблему обходит: лобби само идёт за данными, `Hub` в лобби не пишет.

### Практика

1. `NewLobby(src tableSource, interval time.Duration)`; `Hub` передаёт себя.
2. В `message.go` константа `TypeLobbyState = "lobby_state"` и структура payload с полями `Online` и `Tables`.
3. В `Run` добавь ветку тикера: собрать сообщение, сравнить с прошлым, разослать при изменении.
4. При `register` новому клиенту сразу отправь **текущий** снимок, не дожидаясь тикера.
5. При изменении онлайна (пришёл новый игрок, ушёл последний вкладкой) разошли всем, не дожидаясь тикера.
6. Тесты с фейковым источником:
   - подключился → первое сообщение `lobby_state` с текущими столами;
   - источник не изменился → новых сообщений нет;
   - источник изменился → пришло новое сообщение.

   Сообщения клиента читай из `c.send`, как в помощнике `lastOfType` из `economy_test.go`.

> [!warning] Ловушки
> - `tables: null` вместо `[]` в JSON, когда столов нет. Фронту удобнее пустой массив; `ListOpenRooms` создаёт срез через `make`, проверь, что так и осталось.
> - Тикер нужно остановить (`defer ticker.Stop()`), иначе утечка.
> - Не вызывай `ListOpenRooms` из `ServeLobby` или из другой горутины «для скорости». Всё про лобби делает `Run`.

### Проверь себя

> [!question]- Почему рассылка из `Run` не должна блокироваться на одном клиенте?
> `Run` — одна горутина на всё лобби. Если она ждёт одного медленного клиента, не обрабатываются ни регистрации, ни выходы, ни рассылки остальным. Один плохой интернет «заморозит» лобби для всех.

> [!question]- Зачем отправлять снимок сразу при подключении?
> Иначе новый клиент до 2 секунд видит пустое лобби, а если ничего не меняется, то не увидит столы никогда: рассылка идёт только при изменении.

> [!question]- Что лучше сравнивать: структуры или байты JSON?
> Структуры с вложенными срезами нельзя сравнить через `==`, понадобится `reflect.DeepEqual` или ручной цикл. Байты сравниваются одной функцией, и их всё равно нужно получить для отправки.

> [!question]- Почему 2 секунды, а не 100 мс?
> Каждый тик берёт блокировку `Hub` и сериализует список. 100 мс дали бы почти ту же картинку для человека, но в 20 раз больше работы. 2 секунды незаметны в лобби и дёшевы.

### Готово, когда

- [ ] тесты рассылки зелёные с `-race`
- [ ] в DevTools → WS → Messages видно `lobby_state` при подключении и при создании стола в другом окне
- [ ] без изменений сообщения не приходят

## Шаг 5. Фронт: useLobbySocket

### Зачем

Лобби показывает столы из сокета, а опрос включается, только если сокет недоступен.

### Теория

> [!note] Composable
> Функция `useXxx()`, которая создаёт реактивное состояние (`ref`) и вешает на жизненный цикл компонента подписки и их снятие (`onUnmounted`). Уже есть похожие: `useGameSocket.ts`, `useTurnAlert.ts`. Повтори их форму, не изобретай новую.

> [!note] Экспоненциальная задержка переподключения
> Сервер перезапустился — сотня клиентов не должна ломиться обратно в ту же миллисекунду. Задержка растёт: 0,5 → 1 → 2 → 4 с, дальше не больше потолка. В `useGameSocket.ts` это `Math.min(500 * 2 ** retries, 4000)`.

> [!note] Плавная деградация
> Если сокет не открылся (прокси, сеть), пользователь должен увидеть столы всё равно. Поэтому опрос не удаляется, а **включается, когда сокет не в состоянии `open`**, и выключается, когда сокет открылся.

### Практика

1. `web/src/composables/useLobbySocket.ts`. Возвращает `tables`, `online`, `status`.
   - URL собери так же, как в `useGameSocket.ts` (протокол `ws`/`wss` по протоколу страницы), путь `/ws/lobby`.
   - В `onmessage` разбери `lobby_state` и обнови `tables` и `online`.
   - `onclose` → переподключение с задержкой; закрывать по-настоящему, только если компонент размонтирован.
   - `onUnmounted`: закрыть сокет, снять таймер.
2. Тип сообщения добавь рядом с типами игры (`web/src/types/game.ts` или отдельный файл), поля как в `RoomInfo`.
3. `LobbyView.vue`:
   - `tables` берутся из сокета;
   - `setInterval` работает, только пока `status !== 'open'` (используй `watch` по статусу);
   - покажи онлайн в шапке лобби, например «В сети: 7».
4. Проверь, что `AllTables.vue` и `TablesCarousel.vue` ничего не заметили: они получают массив столов пропсом, источник им не важен.

> [!warning] Ловушки
> - Два источника пишут в один `tables`: опрос вернулся позже сокета и затёр свежие данные старыми. Подумай, нужен ли опрос вообще, когда сокет открыт (не нужен).
> - Обработчики старого сокета после переподключения. В `useGameSocket.ts` это решено проверкой `if (ws !== socket) return`; разберись, зачем она.
> - Сокет переживает уход со страницы, если забыть `onUnmounted`. Проверь: ушёл за стол → в DevTools лобби-сокет закрыт.

### Проверь себя

> [!question]- Зачем проверка `ws !== socket` в `onclose`?
> Если успели создать новый сокет, а старый закрылся позже, его `onclose` не должен запускать ещё одно переподключение и сбрасывать состояние. Проверка отсекает события «чужого», уже заменённого сокета.

> [!question]- Почему таблицам-компонентам не пришлось меняться?
> Они получают данные пропсами и не знают, откуда те пришли. Разделение «кто достаёт данные» и «кто рисует» окупилось.

> [!question]- Что увидит пользователь, если сервер упал на 10 секунд?
> Статус «переподключение», список столов остаётся последним известным, включается опрос (он тоже будет падать, пока сервер лежит). Сервер поднялся — сокет переподключится, опрос выключится.

### Готово, когда

- [ ] в Network нет запросов `GET /tables` по таймеру, пока сокет открыт
- [ ] сервер остановлен → опрос включился; сервер запущен → сокет вернулся, опрос выключился
- [ ] онлайн-счётчик меняется, когда открываешь лобби во втором браузере
- [ ] `npm run build` в `web/` проходит без ошибок типов

## Шаг 6. Проверка и защита

### Ручная проверка

1. Два браузера (или обычное окно и инкогнито), два аккаунта, оба в лобби → «В сети: 2».
2. Первый создаёт стол → у второго стол появился за ≤ 2 с без перезагрузки.
3. Второй сел за стол → стол исчез из списка у обоих (заполнен или начался).
4. Закрыть одно окно → у другого «В сети: 1».
5. Остановить сервер → статус «переподключение»; запустить → всё вернулось.

### Коммиты

Маленькими шагами, по одному на шаг плана. Например:

```
feat(ws): lobby loop with online count
refactor(ws): client talks to an endpoint instead of a room
feat(ws): /ws/lobby endpoint with cookie auth
feat(ws): broadcast open tables from the lobby
feat(web): live lobby over websocket with polling fallback
```

### Вопросы комиссии

> [!question]- Почему не опрос с клиента, ведь это проще?
> Каждый клиент делал бы запрос раз в N секунд, нагрузка растёт с числом игроков, и обновления приходят с задержкой. С сокетом сервер считает список один раз и рассылает только при изменении, а заодно знает, кто онлайн, что нужно для друзей.

> [!question]- Почему лобби само опрашивает столы, а не получает события от комнат?
> Одна точка вместо десятка мест в коде комнаты, невозможно забыть событие. Цена — задержка до 2 секунд, в лобби она незаметна.

> [!question]- Как без мьютексов избегаете гонок в лобби?
> Список подключённых принадлежит одной горутине; остальные шлют ей просьбы через каналы. Проверено детектором гонок `go test -race`.

> [!question]- Что будет при тысяче игроков в лобби?
> Одна горутина рассылает один и тот же срез байтов, `Send` не блокируется. Узкое место раньше будет в одном процессе сервера вообще; для нескольких серверов понадобится общая шина (например, Redis pub/sub). Для проекта это сознательное упрощение.

> [!question]- Как защищён сокет лобби?
> Авторизация по cookie `accessToken` до рукопожатия, проверка `Origin`, токен не передаётся в URL.

## Словарь

| Термин | Коротко |
|---|---|
| Горутина-владелец | одна горутина владеет данными, остальные шлют ей просьбы |
| `select` | ждать несколько каналов, выполнить готовый |
| Канал-запрос | отправить владельцу канал, в который он положит ответ |
| Гонка данных | одновременный доступ к памяти, хотя бы один пишет |
| Неявный интерфейс | тип подходит, если у него есть методы; `implements` не нужен |
| Upgrade | превращение HTTP-запроса в WebSocket, ответ `101` |
| Ping / pong | проверка, что соединение живо |
| Fan-out | один снимок рассылается многим |
| Backoff | растущая задержка перед повтором |
| Плавная деградация | при отказе части системы продукт работает хуже, но работает |
